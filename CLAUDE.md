# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

SAR Tracker is a static single-page dashboard (no build step, no npm) that displays Taiwan SAR satellite acquisition frames on a Leaflet map. It is deployed as a GitHub Pages site directly from the `main` branch.

**Stack:** plain HTML + vanilla JS + CSS. No framework, no bundler, no package.json. Leaflet 1.9.4 loaded from unpkg CDN.

## Development

Open `index.html` directly in a browser (`file://`) or serve it locally:

```bash
python serve.py
# then open http://localhost:8080
```

`serve.py` is `http.server` plus `Cache-Control: no-store`. Use it rather than `python -m http.server`: browsers cache `app.js` indefinitely otherwise, so edits appear not to take effect until a hard refresh (Ctrl+Shift+R). The data files are already fetched with `cache: 'no-cache'` by `app.js`.

No build, lint, or test commands exist. Changes are live-reloaded by refreshing the browser. Deploy = `git push origin main` (GitHub Pages auto-deploys).

When running locally via `file://`, data is loaded from `data/sar_status.js` (a `window.__SAR_DATA = {...}` assignment). On the web, data loads from `data/sar_recent.json` first (last 14 days, fast), then upgrades to `data/sar_status.json` in the background with a progress bar.

## Architecture

Everything lives in three files:

| File | Purpose |
|------|---------|
| `index.html` | Static shell: header, sidebar, map container, stats panel, mobile nav. No dynamic content. |
| `app.js` | All application logic (~3 000 lines). Sections are delimited by `// ═══` banners. |
| `styles.css` | All styles (~2 100 lines). Three responsive breakpoints: default (desktop), `≤980px` (tablet), `≤640px` (mobile). |

`data/sar_status.js` and `data/sar_status.json` / `sar_recent.json` are generated by `fetch_sar_data.py` and committed daily; do not hand-edit them.

### Data fetching (`fetch_sar_data.py`)

Sentinel-1 and NISAR have **separate settings and separate workflows** (the `MISSIONS` registry). They are queried, filtered and stored independently — do not merge their query paths:

| | Sentinel-1 | NISAR |
|---|---|---|
| ASF geography | `relativeOrbit` + `frame` | `relativeOrbit` + `frame` |
| Copernicus geography | `intersectsWith` Taiwan WKT | n/a |
| `processingLevel` | server-side | client-side (server-side 504s) |
| Window | ~2 y per track | whole period, 1 request per track |
| Extra filter | footprint centroid bbox | `TAIWAN_NISAR_FRAME_SPECS` allowlist |
| Sources | ASF + Copernicus | ASF only |

ASF latency is dominated by a fixed per-request cost, not window length; a comma-separated `relativeOrbit` list makes ASF build a much slower OR query. Hence one request *per track* covering a long period.

**Sentinel-1 frame numbers encode latitude, relative orbits encode longitude.** Frames 67–83 (ascending) / 503–520 (descending) select the Taiwan *latitude band on any orbit*, so `TAIWAN_S1_FRAME_SPECS` may only list orbits whose ground track actually crosses Taiwan — T69, T142, T171 (ASC) and T105 (DESC). Adding e.g. T42 pulls in scenes over Pakistan, T98 over the Ryukyus. Rarer tracks that merely clip the bbox (T3/T32/T42/T98/T134) still arrive through the Copernicus query, which stays geographic because Copernicus records carry **no frame number at all**.

`is_taiwan_s1_frame()` centroid-checks **both** latitude and longitude — the longitude bound is what stops a mis-specified orbit leaking far-away scenes now that the ASF query is not geographic. It is calibrated to Sentinel-1 frame geometry and must never be applied to NISAR (whose frames span ~2.7° of latitude).

Each mission owns a catalog under `data/catalog/<mission>.json` (gitignored local build state, migrated automatically from the legacy `data/catalog_db.json`). Download lists are written per source *and* per mission to `data/meta4/<source>_<mission>.meta4`.

```bash
python fetch_sar_data.py                    # both missions
REBUILD_SCOPE=nisar python fetch_sar_data.py    # one mission; other's catalog reused
FORCE_FULL_REBUILD=1 REBUILD_SCOPE=nisar python fetch_sar_data.py   # ignore watermark
```

### `app.js` section map (top → bottom)

1. **`SATS` array** — static satellite catalogue (id, band, agency, status, `asf_prefix[]`, bilingual descriptions)
2. **`TRANSLATIONS`** — all UI strings in `en` and `zh-TW`; accessed via `t(key, vars)`
3. **Global constants** — `FEATURED_SATELLITES`, `OPEN_DATA_SATELLITES`, `PLATFORM_COLORS`, `NISAR_TRACK_COLORS`, `APP_VERSION`
4. **`state` object** — single mutable app state; `ensureAdvancedState()` lazily adds filter sub-keys
5. **Data loading** — `loadData()` / `applyFrameData()` / `reconcileFrameMetadata()` / `enhanceFrame()`
6. **Map** — Leaflet init, polygon rendering, selection, highlight styles, drawer open/close
7. **Sidebar & filters** — satellite list, band/tab chips, advanced filters (date, track, frame, product type, direction)
8. **Download / export** — URL copy, CSV export, export panel

### Key patterns

**Re-render pattern:** Controls (chips, selects, buttons) call a state-mutation function that ends with `renderStatsPanel()`. `renderStatsPanel` saves `body.scrollTop`, replaces `body.innerHTML` with freshly-built HTML, restores scroll, then re-renders the SVG chart in a `requestAnimationFrame`. Because innerHTML replacement detaches nodes before bubbling completes, the document-level click-outside handler uses `event.composedPath().includes(statsPanel)` — not `contains()`.

**i18n:** All UI text goes through `t(key)`. Add keys to both `en` and `zh-TW` blocks in `TRANSLATIONS`. `data-i18n="key"` attributes on static HTML are updated by `applyI18n()`.

**NISAR uses its own metadata scheme — do not reuse the Sentinel-1 fields.** ASF returns `polarization`, `beamModeType` and `sizeMB` as *null* for NISAR; it publishes `frameCoverage`, `mainBandPolarization`, `sideBandPolarization`, `rangeBandwidth`, `crid`, `orbitType`, `pgeVersion` and a `bytes` dict instead (size comes from the HDF5 entry, not the browse PNGs). `process_nisar_feature()` in `fetch_sar_data.py` is separate from `process_asf_feature()` for this reason, and `buildFrameMetaRows()` in `app.js` renders NISAR's fields rather than the S1 shape.

**Release tiers:** NISAR data is published in stages, encoded in ASF's `collectionName` (`NISAR_L1_RSLC_BETA_V1` vs `..._PROVISIONAL_V1`) — *beta* (Feb 2026 release, **uncalibrated**) and *provisional* (20 Jul 2026 release). `getNisarRelease()` reads the tier from the data rather than hardcoding dates, and the drawer shows it as a `.rel-badge` sticker beside the granule name. In the current catalog beta covers acquisitions Oct 2025–Jan 2026 and provisional Jun–Jul 2026, with no product in both.

Granule names follow [the ASF convention](https://nisar-docs.asf.alaska.edu/naming-conventions/):
`NISAR_IL_PT_PROD_CYL_REL_P_FRM_MODE_POLE_S_Start_End_CRID_A_C_LOC_CTR` — where `IL` is instrument+level (`L1` = L-SAR, level 1), `REL` is the **track** and `FRM` the **frame** (not the reverse), `MODE` is the per-band bandwidth in MHz (`2005` → `20+5`), `POLE` is a 2-char polarization code per band (`DHDH` → `HH,HV / HH,HV`), `S` is source, `A` accuracy, `C` coverage (`F`/`P`), `LOC` location. GUNW interferograms use a **longer layout** (20 fields: an extra secondary cycle and a second date pair), so decode the trailing five fields anchored to the end of the array.

**Sidebar filters are split per mission**, into `#product-section` ("Sentinel-1 Options", `renderFormatOptions`) and `#nisar-section` ("NISAR Options", `renderNisarOptions`). Each hides itself when its mission has no frames in `getFormatPoolFrames()` (which honours band/tab/satellite), and clears its selections when hidden so invisible chips can never filter the map.

Product types are tracked in **two Sets** — `filters.formats` (Sentinel-1) and `filters.nisarFormats` — because the catalogues share no product types; one combined Set meant selecting `SLC` hid every NISAR frame. `frameMatchesAdvancedFilters` picks the Set via `isNisarFrame(frame)`. Both seed from `DEFAULT_PRODUCT_TYPES_BY_SATELLITE` (SLC / RSLC by default).

**Every chip group is an explicit selection that can be emptied.** Defaults are applied exactly once per group, tracked by `filters.seeded`; re-seeding whenever a Set went empty made the last chip un-clickable (it snapped straight back on). An empty group therefore means "match nothing", not "no restriction" — the same rule holds for the stats satellite/track chips, which no longer keep a minimum of one. A frame is still never excluded on a field it does not carry (SME2 has no range bandwidth).

NISAR additionally has `nisarCoverage` and `nisarBandwidth`: one overpass ships several products differing only in *frame coverage* (Full / Partial) and *bandwidth mode* (`20+5`, `40+5`, …), so the same track/frame/time appears more than once and product type alone cannot separate them. Sentinel-1 has no such fields and must never be filtered by them. For these two, an empty Set means "no restriction" (all chips render active); product-type Sets instead hold an explicit selection.

**Footprints must be normalised to Polygon.** Copernicus returns some scenes as a one-part `MultiPolygon`. Only `Polygon` is handled by the centroid filter, the slim export (`fp`) and the Leaflet renderer, so an un-normalised MultiPolygon both **skips the Taiwan bbox check** and **never draws** while still counting in filters, stats and exports. `normalize_footprint()` (Python, applied at ingest *and* in `refresh_derived_fields`) and `normalizeFootprint()` (JS, applied in `enhanceFrame` and the render loop) collapse it to the largest ring.

**Frame data shape** (post-`enhanceFrame`): `satellite_id`, `platform`, `date` (ISO string), `path_number_norm` (integer track), `direction_norm` (`ASCENDING`/`DESCENDING`), `frame_number_norm`, `is_open_data`, `track_label` (`A69`, `D105`, `OTHER_S1`, `NISAR`, …)

**Taiwan Sentinel-1 tracks:** the fetch script covers T69 (ASC), T105 (DESC), T142 (ASC), T171 (ASC — the data says ascending) via `TAIWAN_S1_FRAME_SPECS`. The **stats panel** charts only the two priority tracks: `STATS_S1_TRACKS = [69, 105]`. NISAR has its own chips, `STATS_NISAR_TRACKS` (A39/A111/D61/D133), keyed by direction+path via `nisarTrackKey()`.

`statsTrackAllowed()` routes by mission — NISAR against `activeNisarTracks`, **any** `S1*` platform (including retired S1B, which appears in the track table) against `activeTracks`. Both the Acquisition Frequency Chart and `buildFrequencyStats()` (Track Statistics) apply it, so the two panels always agree.

**Stats chart cells are sized in HOURS** (`STATS_CELL_STEPS`, 1 h → 30 d; `statsCellHours()`), so the chart can resolve individual overpasses — Taiwan passes cluster at ~05 h and ~18 h local. Bucketing is timestamp-based and single-pass (a year at 1 h is ~8 800 buckets, so comparing every frame against every bucket is far too slow). Anything consuming a bucket must compare **timestamps, not `date.slice(0,10)`**: a sub-day cell starts and ends on the same calendar day, so date-string ranges match nothing.

**Chart appearance is user-tunable** from the **gear button in the stats panel header**, which opens the `#stats-style-pop` popover (`renderStatsStylePanel`). It holds two sections: *Series Colors* (per-satellite, `sar_sat_colors`) and *Appearance* (`CHART_STYLE_DEFAULTS` / `CHART_STYLE_RANGES` — bar width/opacity, day shading, grid opacity/width, label size, min bar width, `sar_chart_style`). Each section shows a Reset only when customised.

The popover lives **outside** `#stats-panel-body`, so `renderStatsPanel()` (which replaces the body's innerHTML) does not destroy it. Setters therefore call `renderStatsChart()` + `renderStatsStylePanel()` rather than `renderStatsPanel()` — a full rebuild would reset the body scroll and tear the popover down mid-drag. Colour changes additionally patch the satellite chips in place via `data-sat-color` / `data-sat-chip`. Style values reach the SVG as `--sc-*` CSS variables, so anything presentational belongs in CSS rather than in the geometry code.

**The chart x-axis adapts to available width.** Sub-day cells get two rows — clean hour steps on top (snapped to a multiple of the cell size, not every Nth bucket) and dates beneath — but only when a day is at least 40 px wide. Below that the hour scale is meaningless, so it falls back to a single row of dates. `labH` changes with the mode, so `barH` must be derived after the mode is known.

**Chart export is WYSIWYG by construction.** `serializeChartSVG()` copies the *computed* value of every drawing-related property (`SVG_EXPORT_PROPS`) onto each cloned element instead of re-declaring a stylesheet — the previous approach hardcoded `font-size: 9px` / `stroke-width: 1` and omitted `.schart-band`, so exports silently lost the day banding and every appearance setting. It also wraps the chart with padding and an opaque panel-coloured background, since a transparent PNG makes the bars unreadable on a light backdrop. `chartToPngBlob()` rasterises that at 2x for Copy/PNG.

Copy uses the async clipboard API, which needs a **secure context and a focused document** — it fails with `NotAllowedError: Document is not focused` under automation. Both copy paths therefore fall back to a download rather than just reporting failure.

**Stats counting:** acquisition counts use one canonical product per mission (`STATS_CANONICAL_PRODUCT` — `SLC` for Sentinel-1, `RSLC` for NISAR), because a single overpass ships as several products and counting all of them multiplies each pass. Use `statsIsCanonicalProduct()` / `statsTrackAllowed()` rather than re-inlining the rule; the track chips govern Sentinel-1 only, since NISAR flies its own tracks. Note the stats **table** (`buildFrequencyStats`) counts distinct dates across *all* product types and tracks, so it legitimately lists rare Copernicus-only tracks (T3/T32/T42/T134) that the chart's chips do not offer.

**Stacking contexts:** `header` z-index 200, stats panel fixed z-index 600, `.map-wrap` uses `isolation: isolate` so internal z-index values (map overlays at 1100–1200) don't escape into the page stacking context.

**Mobile layout (≤640px):** `.hdr-controls` is hidden; `.sidebar` and `.map-wrap` are `position: absolute; inset: 0` within a `position: relative` `.layout`. Navigation is the bottom `.mob-nav` tab bar (z-index 800). The stats panel has `bottom: 52px` to sit above the tab bar.
